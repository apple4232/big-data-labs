# Week 4 관찰 기록

## Task 1
Bloom은 add 때 켠 비트를 지우지 않고 같은 hash 위치를 조회하므로 삽입 항목의 false negative가 없다. m=8192, k=5, n=800에서 예측 오탐률은 0.860%, 2만 비삽입 질의의 실측은 0.900%로 표본 변동 범위였다.
FM은 64개 최대 trailing-zero R을 8개씩 묶어 평균 R의 중앙값을 취한 뒤 지수화하고 max-R의 점근적 bias를 보정했다. 동일 검증 자료에서 2^R 산술평균 48,608, 중앙값 32,768, 선택한 방법 24,915 / truth 19,953였다.
Reservoir는 현재 i번째 항목에서 randrange(i)<k일 때 해당 slot을 교체한다. 새 항목이 들어올 확률 k/i와 이전 항목의 생존확률을 곱하면 최종 k/n이 되므로 n을 미리 몰라도 k개만 보관한다. 제공된 4,000회 uniform 검증도 통과했다.

## Task 2
이 PC에서 n=6,400,000의 exact 집계는 63.88초로 시간 부담이 컸고 peak은 188.29MB였다. 2,500만 건 추가 실행은 60.97초의 시간 경계에서 중단했으며, OOM은 관측하지 않았다.
완료된 64배 크기 범위의 메모리 log-log 기울기는 exact=0.931, FM=0.0010로 측정됐다. exact는 distinct 수에 대략 선형으로 증가했고 FM은 64개 register를 고정하여 약 9.44KiB를 유지했지만 실행시간은 더 길었다.
크기별 FM / truth는 0.843×, 0.918×, 0.842×, 1.141×로 n 증가에 따른 단조 개선은 없었다. 두 배 오차는 방문자 규모의 대략적인 자원 계획에는 허용할 수 있지만 사용자별 과금이나 작은 증감 비교에는 허용하기 어렵다.

## Task 3
p(k)=(1-exp(-kn/m))^k를 최소화하면 k*=(m/n)ln2이다. 10 bits/item에서는 6.931→7개 hash를 사용했고, shared code를 제외한 모든 retained 상태(인스턴스+seed 포함 bytearray)를 합산해 정확히 80,000비트였다.
표준 Bloom 모형의 최적 예측값은 exp(-10(ln2)^2)=0.819%이다. 실제 유효 공간은 79,160비트여서 k=7의 예측은 0.862%이며 실측 1,717/200,000=0.8585%, false negative 0으로 strong 기준을 충족했다. 유한 질의 표본의 실측은 이론의 기대값과 동일할 필요가 없다.
n이 미지라면 점유율과 예상 상한을 감시하고, 예산을 늘릴 수 있을 때 scalable Bloom을 고려한다. n을 낮게 잡으면 오탐이 증가하고, 목표 오탐률에 맞춘 공간을 너무 크게 잡으면 RAM을 낭비한다. 고정 예산이 가득 찬 경우 과거 비트를 지워 정확한 membership 계약을 깨는 대신 오탐 증가를 인정해야 한다.
